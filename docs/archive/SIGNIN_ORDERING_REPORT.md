# Sign-in and ordering inspection — 8 October 2026

Work stays on `launch-readiness`. No production deployment, migration, billing change, email send, account creation/confirmation override, order or file upload was performed by this investigation.

## Findings

1. **Reproduced locally:** an authenticated customer returning to `/account` still saw the sign-in/create form. The page showed a signed-in message but kept asking for credentials.
2. **Reproduced locally:** another tab signing in as the same customer cleared the first tab's visible drafts/orders. Its loading effect depended only on the unchanged UUID, leaving the page empty until polling or focus reloaded it.
3. Standalone sign-in used a whole-document reload and defaulted to My orders even when a same-device checkout was waiting for that email. Confirmation-required signup left the create mode active instead of presenting the next sign-in step.
4. **Hosted read-only inspection:** the owner-supplied customer account exists and Supabase marks its email confirmed. Only these booleans were read; no identifying account fields or credentials are recorded here. This differs from the owner's recollection of pending confirmation; no account state was changed.
5. **Hosted ordering blocker:** migrations remain 001–006. `public.order_applications`, `get_order_settings()` and `get_my_orders()` are absent. Successful Supabase authentication cannot complete this branch's hosted ordering workflow until 007–009 are reviewed/applied and verified.
6. **Production/frontend mismatch:** the deployed `https://edgetapflow.web.app/account` public bundles contain Firebase Auth and do not contain the approved Supabase destination. That release does not share this branch's Supabase login. Anonymous account/order screens returned successfully without browser exceptions; no real password was submitted there.
7. Port 3000 currently belongs to an unrelated local application; `/account` returns 404 there. It was left untouched. EdgeTap QA runs separately on port 4173.

## Changes

- `/account` waits for the initial session, then shows either the signed-out form or a signed-in account view with explicit continue/order/sign-out actions. Existing sessions and email-link sessions no longer ask for the password again.
- Sign-in uses an internal `router.replace` transition, holds the submission lock through navigation and clears the password after success. Confirmation-required signup switches to sign-in and clears the password without creating an order/profile.
- An unspecified return route resumes a guest checkout only when its claimed email matches the authenticated email. Explicit return routes remain allowlisted; external/arbitrary destinations fail closed. A different account cannot automatically claim another checkout.
- Repeated same-account events retain the orders/drafts UI. Responses from a previous account are discarded even while UI cleanup is pending. Real account changes/sign-out still clear private data immediately. Initial loading and service errors no longer falsely show an empty-order success state; retry is explicit.
- Auth user identity remains stable when the UUID/email are unchanged, while all auth events still reach subscribers so staff/recovery checks continue. Subscriber work runs in a subsequent task and catches both synchronous/asynchronous errors. This is defensive scheduling, not a claimed reproduced SDK deadlock; see the [official Supabase troubleshooting guidance](https://supabase.com/docs/guides/troubleshooting/why-is-my-supabase-api-call-not-returning-PGzXw0).
- Pre-payment sign-in has password recovery, serialized submissions, disabled working fields and actionable confirmation/credential/rate-limit errors. Recovery preserves the device draft; the UI conditionally asks the user to check email rather than claiming delivery.
- Missing ordering RPC/schema errors identify an ordering-service failure after sign-in, retain device details/files and keep payment unavailable. Internal schema/SDK details are hidden; WhatsApp handoff remains available. Memory-only drafts are explicitly described as page-only.
